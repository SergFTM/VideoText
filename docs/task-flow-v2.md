# Флоу работы над задачами — v2

Канонический источник для режимов expand-артефактов (ресерч / репорт / ТЗ /
UI/UX / алгоритмы / AI-скиллы). Промпты в `local_llm.py` выравниваются по этому
документу. Слой «управляемого конвейера» (порядок этапов + чеклисты готовности +
обратные петли) — отдельный будущий этап (layer 3), здесь зафиксирован как
требования.

## 1. Общая логика конвейера

```
1. Ресерч      → сбор и структурирование информации
2. Репорт      → выводы и рекомендации по ресерчу
3. ТЗ          → постановка задачи на реализацию
4. UI/UX       → описание интерфейсного сценария (если нужен интерфейс)
5. Алгоритмы   → пошаговое описание логики действий
6. AI-скиллы   → повторяемые инструкции для AI
7. Реализация  → Claude Code / разработка
```

**Ключевое правило:** нельзя переходить к следующему этапу без явного закрытия
предыдущего. Переход фиксируется чеклистом готовности (раздел 3).

## 2. Контекст на входе каждого режима

| Контекст | Что это | Когда использовать |
|---|---|---|
| бриф | Краткое описание задачи (цель, суть, ограничения) | Когда задача сформулирована чётко |
| расшифровка | Транскрипт голосового/текстового потока мыслей | Когда есть сырой материал без структуры |
| бриф + расшифровка | Оба источника | Когда есть задача + контекст обсуждения |

Режим AI обязан явно указать, из какого контекста берёт входные данные.

## 3. Чеклисты готовности к переходу

**Ресерч → Репорт:** описана предметная область; перечислены варианты решения
(минимум 2); указаны ограничения и риски; сформулированы открытые вопросы; указаны
источники/наблюдения.

**Репорт → ТЗ:** сформулирован чёткий вывод (что рекомендуется); обоснован выбор
варианта; указаны следующие действия; решение согласовано / принято к разработке.

**ТЗ → Алгоритмы:** определены цель и пользователь; перечислены все функциональные
требования; указаны сценарии использования; определены критерии приёмки.

**Алгоритмы → AI-скиллы:** алгоритм описывает одно конкретное действие (не
смешанное); действие повторяется 3+ раза; входные данные чётко определены; формат
результата зафиксирован.

## 4. За что отвечает каждый режим

### Ресерч
Задача: собрать и первично структурировать информацию.
Что делает: выделяет суть; ищет аналоги и лучшие практики; выявляет ограничения и
риски; формулирует открытые вопросы; структурирует материал.
Формат: Задача / Контекст / Варианты решения / Ограничения / Риски / Источники-
наблюдения / Открытые вопросы.
Что НЕ делает: не делает выводы и не рекомендует решение; не пишет ТЗ; не
придумывает реализацию.

### Репорт
Задача: сделать выводы по результатам ресерча.
Что делает: анализирует варианты; сравнивает плюсы/минусы; даёт чёткую
рекомендацию; обосновывает выбор; описывает следующие шаги.
Формат: Краткое резюме (2-3 предложения) / Что исследовали / Основные выводы /
Варианты решений + плюсы-минусы каждого / Риски / Рекомендация + обоснование /
Следующие действия.
Что НЕ делает: не пишет ТЗ; не описывает реализацию; не перечисляет всё найденное
без выводов.

### ТЗ
Задача: зафиксировать постановку задачи на реализацию.
Что делает: формулирует цель и контекст; описывает пользовательские сценарии;
перечисляет функциональные требования; фиксирует ограничения; указывает критерии
приёмки.
Формат: Название задачи / Цель / Пользователь-заказчик / Пользовательские сценарии /
Функциональные требования / Нефункциональные требования / Ограничения / Используемые
данные / Критерии приёмки / Что не входит в скоп.
Что НЕ делает: не описывает порядок реализации (это алгоритм); не рекомендует
технологии (это репорт); не описывает интерфейс детально (это UI/UX).

### UI/UX
Задача: описать интерфейсный сценарий взаимодействия пользователя с функцией.
Нужен только когда задача предполагает пользовательский интерфейс.
Входные: ТЗ + алгоритмы (пользовательские сценарии).
UI-слой: какие экраны нужны; какие элементы на каждом экране; какие состояния
(загрузка/ошибка/успех/пусто); какие сообщения видит пользователь.
UX-слой: что пользователь делает первым; что происходит после каждого действия; где
нужна подсказка/подтверждение/предупреждение; где можно упростить путь.
Формат: Экран / Цель экрана / Элементы / Кнопки и действия / Состояния
(загрузка/успех/ошибка/пустое) / Переходы (при успехе → / при ошибке →).
Что НЕ делает: не описывает внутреннюю логику; не является алгоритмом обработки
данных; не заменяет ТЗ.

### Алгоритмы
Задача: пошагово описать, что именно происходит — в системе, у пользователя или в
AI-процессе.
Входные: ТЗ + UI/UX (для пользовательских алгоритмов).
Типы: 1) пользовательский — что делает пользователь шаг за шагом; 2) системный —
что делает приложение внутри; 3) AI-алгоритм — как AI обрабатывает конкретную задачу;
4) технический — как модуль выполняет операцию.
Формат: Название алгоритма / Тип / Цель / Предусловия / Входные данные / Шаги /
Правила и условия (если [условие] → [действие]) / Критерии выхода / Результат /
Граничные случаи / Ошибки и обработка.
Что НЕ делает: не является ТЗ (не фиксирует требования); не является AI-скиллом (не
повторяемая инструкция).

### AI-скиллы
Задача: превратить повторяемое действие в стабильную инструкцию для AI.
Условие появления: только после ресерч → репорт → ТЗ → алгоритм.
Критерий необходимости: действие будет выполняться 3+ раза в разных контекстах.
Формат: Название скилла / Версия / Когда использовать / Когда НЕ использовать /
Входные данные (обязательные / опциональные) / Что делать (шаги) / Что не делать /
Формат результата / Критерии качества / Примеры (Вход / Выход).
Что НЕ делает: не заменяет алгоритм; не является ТЗ; не создаётся из сырой идеи без
предварительных этапов.

## 5. Обратные петли

- Ресерч показал, что идея нежизнеспособна → стоп; возврат к брифу, переформулировка.
- Репорт не даёт однозначной рекомендации → дополнительный ресерч по открытым вопросам.
- ТЗ содержит противоречия → возврат к репорту, уточнение решения.
- Алгоритм не покрывает граничные случаи → доработка алгоритма; не переходить к AI-скиллу.
- AI-скилл даёт нестабильные результаты → пересмотр алгоритма; уточнение формата входных.

## 6. Рабочие сценарии

- **Новая задача (полный цикл):** идея → расшифровка → ресерч → репорт → ТЗ →
  (UI/UX если нужен) → алгоритмы → AI-скиллы → Claude Code.
- **Уже есть ТЗ:** загрузить ТЗ → проверить полноту по чеклисту → алгоритмы →
  AI-скиллы → Claude Code.
- **Существующий проект (аудит):** ресерч (аудит) → репорт (проблемы/возможности) →
  ТЗ (изменение) → алгоритмы (безопасные изменения) → AI-скиллы → Claude Code.
- **Срочная задача (без полного цикла):** разрешено ТЗ → Алгоритмы → Реализация;
  условие: задача хорошо известна, ресерч не нужен; риск: пробелы в требованиях;
  контроль: чеклист ТЗ обязателен перед переходом к алгоритмам.

## 7. Главные разграничения

| Режим | Вопрос, на который отвечает | Результат |
|---|---|---|
| Ресерч | Что это и какие есть варианты? | Структурированные данные |
| Репорт | Что выяснили и что рекомендуем? | Документ для принятия решения |
| ТЗ | Что именно нужно сделать? | Постановка задачи для разработки |
| UI/UX | Как пользователь взаимодействует? | Интерфейсный сценарий |
| Алгоритмы | Что происходит шаг за шагом? | Пошаговое описание логики |
| AI-скиллы | Как автоматизировать повторение? | Инструкция для стабильного вывода |

## 8. Ключевое правило

Нельзя смешивать режимы в одном запросе. Сначала понять (ресерч) → потом вывод
(репорт) → потом поставить задачу (ТЗ) → потом интерфейс (UI/UX, если нужен) → потом
алгоритм (алгоритмы) → потом автоматизировать (AI-скиллы).
